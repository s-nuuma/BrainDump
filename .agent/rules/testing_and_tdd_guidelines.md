# テスト設計 ＆ テスト駆動開発 (TDD) ガイドライン (testing_and_tdd_guidelines.md)

このルールは、テストコード（`**/*.test.ts`, `**/*.test.tsx`, `**/e2e/**/*.spec.ts` などのテストファイル）の作成・編集時に発動します。

---

## 1. ユニットテスト (Vitest) と E2Eテスト (Playwright) の責任分離

テストの実行コストを抑え、安定したテスト駆動開発（TDD）を行うための役割定義です。

- **ユニットテスト (Vitest) の責務**:
  - 純粋なビジネスロジック、データ整形ユーティリティ、カスタムフック、およびステートのない純粋なUIコンポーネントを対象とします。
  - テスト実行がミリ秒単位で高速に終わるように設計してください。
- **E2Eテスト (Playwright) の責務**:
  - ページを跨いだユーザー遷移フロー、複雑な認証・認可ガード、Firestore と連動した実画面の描画・操作検証（統合テスト）を対象とします。
  - AIエージェントがブラウザ（Manager Surface）で視覚的検証を行う際の基準として、シナリオテストを構築します。

---

## 2. 外部API・Firebase のモック（Mock）方針

テスト実行時に本番環境への予期せぬアクセスや課金が発生するのを防ぐルールです。

- **モックの徹底**:
  - ユニットテスト内では、Firebase Authentication や Cloud Firestore へのアクセスは必ずモック（Mock）またはスタブ（Stub）に置き換えてください。
  - APIクライアント（Google Gen AI SDKや自作のAPIクライアントなど）も必ずテスト内でモック化し、実際のネットワークリクエストが送信されないことを確認してください。

---

## 3. E2Eテスト用のマークアップ規約 (`data-testid`)

Playwright で画面上の要素を正確かつ堅牢にキャッチするための要素特定ルールです。

- **`data-testid` の付与**:
  - フォームの送信ボタン、入力フィールド、モーダルウインドウなど、テスト時のトリガーとなる重要なUI要素には、必ず `data-testid` 属性（例: `data-testid="submit-button"`）を付与してください。
  - テストコード側では、CSSクラス名（`.bg-blue-600` 等）や曖昧なテキストマッチではなく、`page.getByTestId('submit-button')` を使用して要素を特定してください。これにより、将来的なデザイン崩れや文言修正によってテストが突然落ちる問題（Flaky Test）を防止します。

```html
<!-- ⭕ 良い実装例 (Good) -->
<button
  data-testid="save-recipe-button"
  className="px-4 py-2 bg-green-500 text-white rounded"
>
  保存する
</button>
```

---

## 4. TDD (テスト駆動開発) プロセス

1. 要件（`spec.md`）が決定または更新されたら、**実装コードを書く前にまずテストを作成（または変更点に追随）**します。
2. テストが失敗すること（Red）を確認したのち、そのテストを通す（Green）ために最小限の実装コードを追加します。
3. テストが通った状態を保ったまま、リファクタリングを進行します。
